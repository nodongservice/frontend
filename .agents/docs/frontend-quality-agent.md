
# Frontend Quality Agent

이 문서는 React/Next.js 프론트엔드 코드를 작성하거나 수정할 때 반드시 지켜야 할 품질 기준이다.

## 기본 원칙

프론트엔드 코드는 단순히 화면이 보이는 수준이 아니라, 실제 서비스 운영을 고려해 작성한다.

특히 다음 항목을 항상 고려한다.

- 렌더링 성능
- API 요청 상태 관리
- 로딩/에러/빈 데이터 처리
- 불필요한 리렌더링 방지
- 사용자 입력 중 중복 요청 방지
- 접근성
- 유지보수 가능한 컴포넌트 분리
- 모바일/반응형 대응
- 예외 상황에서의 UX

## 렌더링 성능 기준

컴포넌트를 작성할 때 불필요한 리렌더링이 발생하지 않도록 한다.

다음 상황을 주의한다.

- 컴포넌트 내부에서 매 렌더링마다 새 객체, 새 배열, 새 함수를 무분별하게 생성하지 않는다.
- props로 내려가는 callback은 필요하면 `useCallback`을 사용한다.
- 계산 비용이 큰 값은 필요하면 `useMemo`를 사용한다.
- 리스트 렌더링 시 `key`는 index가 아니라 고유 id를 우선 사용한다.
- 큰 리스트는 pagination, infinite scroll, virtualization 적용 가능성을 고려한다.
- 상태는 필요한 가장 가까운 위치에 둔다.
- 전역 상태는 꼭 여러 화면/컴포넌트에서 공유해야 할 때만 사용한다.
- 단순 UI 상태까지 무조건 Zustand/Redux 등에 넣지 않는다.

단, `useMemo`, `useCallback`, `memo`는 무조건 사용하는 것이 아니라 실제 리렌더링 비용이 있거나 props 안정성이 필요한 경우에만 사용한다.

## API 요청 상태 관리

API 요청이 있는 화면은 반드시 상태를 구분한다.

최소한 다음 상태를 고려한다.

- idle: 아직 요청 전
- loading: 요청 중
- success: 요청 성공
- error: 요청 실패
- empty: 성공했지만 데이터 없음
- refetching: 기존 데이터가 있는 상태에서 재요청 중
- disabled: 조건이 충족되지 않아 요청하지 않음

TanStack Query를 사용하는 경우 다음을 고려한다.

- `isLoading`, `isFetching`, `isError`, `isSuccess`를 구분한다.
- 최초 로딩과 재요청 로딩을 구분한다.
- 검색/필터 조건이 있을 경우 query key를 명확히 분리한다.
- 불필요한 refetch가 발생하지 않도록 `enabled`, `staleTime`, `gcTime`을 적절히 설정한다.
- mutation 후에는 필요한 query만 invalidate한다.
- 실패 가능성이 있는 요청은 사용자에게 이해 가능한 에러 메시지를 보여준다.
- 같은 API 요청 로직을 여러 컴포넌트에 중복 작성하지 않고 hook으로 분리한다.

## UI 상태 처리 기준

모든 주요 화면은 다음 UI 상태를 가진다.

### Loading

데이터를 불러오는 중임을 사용자에게 보여준다.

가능하면 단순 텍스트보다 skeleton, spinner, placeholder 중 상황에 맞는 방식을 사용한다.

### Error

API 실패, 권한 없음, 서버 오류, 네트워크 오류를 구분할 수 있으면 구분한다.

에러 화면에는 가능하면 다음 요소를 포함한다.

- 사용자가 이해할 수 있는 메시지
- 다시 시도 버튼
- 필요 시 이전 화면으로 돌아가기 버튼

### Empty

데이터가 없는 경우 빈 화면을 방치하지 않는다.

예시:

- 검색 결과가 없습니다.
- 등록된 공고가 없습니다.
- 아직 추천 결과가 없습니다.
- 필터 조건을 변경해보세요.

### Success

데이터가 정상적으로 있을 때만 본문 UI를 렌더링한다.

데이터가 없을 가능성이 있는 필드는 optional chaining 또는 fallback text를 사용한다.

## 사용자 액션 상태

버튼, 폼, 검색, 제출 기능은 중복 요청을 방지한다.

- 제출 중에는 버튼을 disabled 처리한다.
- mutation 진행 중에는 중복 클릭을 막는다.
- 저장/삭제/수정 성공 후 사용자에게 결과를 알려준다.
- 실패 시 조용히 무시하지 않고 에러 메시지를 보여준다.
- 검색 입력은 필요하면 debounce 처리한다.
- 필터 변경 시 과도한 API 호출이 발생하지 않도록 한다.

## 컴포넌트 분리 기준

페이지 컴포넌트에 모든 로직과 UI를 몰아넣지 않는다.

권장 구조:

- page: 라우팅 단위
- feature: 도메인 단위 기능
- component: 재사용 UI
- hook: API 요청/상태 로직
- service/api: HTTP 요청 함수
- schema/type: 타입과 검증 스키마

예시 구조:

- `pages` 또는 `app`: 라우팅 진입점
- `features/auth`
- `features/jobs`
- `features/accessibility`
- `components/common`
- `components/layout`
- `hooks`
- `api`
- `types`

## React/Next.js 작성 기준

React 단독 프로젝트에서는 CSR 기준으로 작성하되, 나중에 Next.js로 이전할 수 있도록 페이지와 컴포넌트를 분리한다.

Next.js 프로젝트에서는 다음을 고려한다.

- SEO가 필요한 페이지는 SSR/SSG/ISR 가능성을 고려한다.
- 로그인 이후 사용자 맞춤 화면은 CSR 중심으로 작성해도 된다.
- `window`, `document`, `localStorage`는 서버 렌더링에서 터질 수 있으므로 직접 접근을 피한다.
- 브라우저 API는 `useEffect` 내부 또는 client component에서만 사용한다.
- 페이지 단위 metadata, loading, error, not-found 처리를 고려한다.

## 폼 처리 기준

폼은 단순 상태 나열보다 React Hook Form 같은 폼 관리 도구 사용을 우선 고려한다.

검증이 필요한 경우 Zod 같은 schema validation을 사용한다.

폼에서는 다음을 처리한다.

- 필수값
- 형식 오류
- 길이 제한
- 서버 응답 에러
- 제출 중 상태
- 제출 성공 후 이동 또는 안내
- 중복 제출 방지

## 접근성 기준

기본 접근성을 무시하지 않는다.

- 버튼은 실제 `button` 태그를 사용한다.
- 클릭 가능한 div를 남발하지 않는다.
- input에는 label 또는 aria-label을 연결한다.
- 모달, 드롭다운, 토스트는 키보드 접근성을 고려한다.
- 색상만으로 상태를 구분하지 않는다.
- 로딩/에러/성공 상태는 시각적으로 명확해야 한다.

## 코드 작성 스타일

코드는 3년차 이상 프론트엔드 개발자가 리뷰한다고 가정하고 작성한다.

다음 코드는 피한다.

- API 상태를 고려하지 않는 코드
- loading/error 없이 바로 data만 렌더링하는 코드
- 중복 요청을 막지 않는 form submit
- props drilling이 과도한 구조
- 한 파일에 지나치게 많은 역할이 섞인 코드
- 타입이 `any`로 방치된 코드
- 임시 하드코딩 값이 설명 없이 남아 있는 코드
- 실패 상황을 console.log만 하고 끝내는 코드

## 코드 리뷰 체크리스트

코드를 작성하거나 수정한 뒤 다음을 확인한다.

- 최초 로딩 상태가 있는가?
- 재요청 중 상태가 있는가?
- 에러 상태가 있는가?
- 빈 데이터 상태가 있는가?
- 버튼 중복 클릭이 막혀 있는가?
- API 요청 key가 명확한가?
- 불필요한 리렌더링이 발생하지 않는가?
- 컴포넌트 책임이 너무 크지 않은가?
- 타입이 충분히 명확한가?
- 나중에 Next.js 라우팅 구조로 옮기기 쉬운가?
- 모바일 화면에서도 깨지지 않는가?
- 사용자가 실패 원인을 이해할 수 있는가?

## 우선순위

기능 구현 시 우선순위는 다음과 같다.

1. 정상 동작
2. 로딩/에러/빈 데이터 처리
3. 중복 요청 방지
4. 컴포넌트 분리
5. 타입 안정성
6. 렌더링 최적화
7. 접근성 개선
8. 테스트 가능성 확보

성능 최적화는 무조건 미리 과하게 적용하지 않는다.  
다만 API 상태 처리, 불필요한 리렌더링 방지, 리스트 key 관리, 요청 중복 방지는 기본 품질로 간주한다.
