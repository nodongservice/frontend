# BridgeWork Frontend Specification

## 1. 문서 목적

이 문서는 BridgeWork 프론트엔드 개발을 위한 기능 명세서이다.

BridgeWork 프론트엔드는 장애인 구직자가 자신의 조건에 맞는 일자리를 찾고, 공고별 접근성 정보와 추천 사유를 이해하며, 지원 전 확인해야 할 항목을 쉽게 파악할 수 있도록 설계한다.

프론트엔드 개발 시 다음 원칙을 따른다.

- 사용자가 입력하지 않아도 기본 일자리 추천을 이용할 수 있어야 한다.
- 장애 유형, 필요한 지원, 선호 업무환경 등 민감할 수 있는 정보는 선택 입력으로 둔다.
- 공고 추천 결과는 점수만 보여주지 않고 이유를 함께 설명한다.
- 지도 정보는 반드시 목록 정보와 함께 제공한다.
- 색상만으로 상태를 표현하지 않는다.
- 모든 주요 화면은 loading, error, empty, success 상태를 구분한다.
- API 호출은 Spring Backend를 통해 수행한다.
- 프론트엔드는 FastAPI AI/GIS Service를 직접 호출하지 않는다.
- WCAG 2.2 AA 수준의 접근성을 고려한다.

---

## 2. 서비스 개요

BridgeWork는 장애인 구직자를 위한 접근성 기반 일자리 추천 서비스이다.

단순히 구인 공고를 나열하는 것이 아니라, 사용자의 장애 유형, 필요한 지원, 선호 업무환경, 거주 지역, 통근 가능 범위, 공공 접근성 데이터를 함께 고려하여 현실적으로 지원 가능한 공고를 추천한다.

프론트엔드는 다음 사용자 경험을 제공한다.

- 온보딩을 통해 사용자 기본 조건과 직장 필터를 설정한다.
- 사용자의 조건에 맞는 일자리 목록을 추천한다.
- 공고별 직무 적합도와 접근성 적합도를 보여준다.
- 지도 기반으로 근무지 주변 접근성 정보를 시각화한다.
- 접근성 점수의 근거, 긍정 요인, 위험 요인, 확인 필요 항목을 설명한다.
- 데이터가 부족한 항목은 “불가능” 또는 “위험”으로 단정하지 않고 “확인 필요”로 안내한다.

## 3. 핵심 사용자

### 3.1 1차 타깃

구직 중인 장애인을 핵심 사용자로 한다.

특히 다음 사용자를 우선 고려한다.

- 중증장애인
- 이동약자
- 지역 기반 취업 희망자
- 직장 접근성을 중요하게 고려해야 하는 구직자

현재 화면에서 고려하는 장애 유형은 다음과 같다.

- 지체장애: 휠체어 사용자
- 시각장애: 전맹, 부분맹, 저시력 사용자
- 청각장애: 청각장애, 농난청 사용자

### 3.2 확장 타깃

직장 접근성을 중요하게 여기는 구직 청년을 확장 타깃으로 본다.

예시는 다음과 같다.

- 통근 시간이 중요한 사용자
- 조용한 근무환경을 선호하는 사용자
- 재택근무, 유연근무, 단축근무를 선호하는 사용자
- 업무환경 리스크를 사전에 알고 싶은 사용자

### 3.3 기관 사용자

향후 다음 기관이 상담 도구로 활용할 수 있다.

- 고용복지플러스센터
- 장애인고용공단 지사
- 지자체 취업지원기관
- 장애인 취업 지원 기관

### 3.4 기업 사용자

향후 장애인 채용을 희망하는 기업도 확장 사용자로 고려한다.

기업은 다음 목적으로 BridgeWork를 활용할 수 있다.

- 자사 공고에 적합한 구직자군 파악
- 장애인 채용 친화 요소 점검
- 지원 전 확인이 필요한 접근성 항목 파악
- 표준사업장, 장애인 전형, 면접 편의 제공 여부 안내

## 4. 프론트엔드 기술 방향

### 4.1 기본 구조

현재 프론트엔드는 React 기반으로 작성한다.

다만 향후 Next.js 페이지 기반 라우팅으로 이전할 수 있도록 다음 구조를 유지한다.

- page 단위 컴포넌트와 재사용 컴포넌트를 분리한다.
- API 호출 로직은 컴포넌트 내부에 직접 작성하지 않고 별도 api 또는 hook으로 분리한다.
- 화면 상태는 loading, error, empty, success로 명확히 나눈다.
- 페이지 컴포넌트가 모든 UI와 로직을 독점하지 않도록 한다.

권장 구조는 다음과 같다.

- `src/pages`: 라우팅 단위 페이지
- `src/components`: 공통 UI 컴포넌트
- `src/auth`: 로그인, 회원가입, 인증 관련 기능
- `src/api`: Spring Backend API 호출 함수
- `src/app`: 앱 라우팅 및 전역 설정
- `src/config`: 환경변수, 상수, 설정값
- `src/utils`: 공통 유틸 함수

### 4.2 API 호출 원칙

프론트엔드는 Spring Backend만 호출한다.

호출 흐름은 다음을 따른다.

Next.js 또는 React Frontend → Spring Backend → FastAPI AI/GIS Service → PostgreSQL/PostGIS

프론트엔드는 FastAPI AI/GIS Service를 직접 호출하지 않는다.

### 4.3 API 상태 처리 원칙

모든 API 요청 화면은 다음 상태를 고려한다.

- idle: 아직 요청 전
- loading: 최초 요청 중
- success: 요청 성공
- error: 요청 실패
- empty: 요청은 성공했지만 데이터 없음
- refetching: 기존 데이터가 있는 상태에서 재요청 중
- disabled: 조건이 충족되지 않아 요청하지 않음

사용자에게 보여지는 주요 화면에서는 최소한 다음 UI를 제공한다.

- 로딩 UI
- 에러 UI
- 빈 데이터 UI
- 정상 데이터 UI

## 5. 전체 화면 목록

BridgeWork MVP 프론트엔드에서 우선 고려하는 화면은 다음과 같다.

| 화면명 | 설명 | 우선순위 |
|---|---|---|
| 랜딩 페이지 | 서비스 소개 및 시작 진입점 | 높음 |
| 로그인 페이지 | 카카오/네이버 로그인 진입 | 높음 |
| 회원가입/온보딩 페이지 | 기본 정보 및 직장 필터 입력 | 높음 |
| 직장 필터 생성 페이지 | 희망 직무, 근무지역, 통근 범위, 필요 지원 입력 | 높음 |
| 추천 일자리 목록 페이지 | 사용자 조건에 맞는 공고 목록 표시 | 높음 |
| 공고 상세 페이지 | 공고 상세, 추천 사유, 접근성 정보 표시 | 높음 |
| 지역 접근성 지도 페이지 | 공고 위치 및 주변 접근성 데이터 표시 | 높음 |
| 마이페이지 | 사용자 정보, 저장 필터, 관심 공고 관리 | 중간 |
| 지원 전 체크리스트 페이지 | 공고 지원 전 확인 사항 제공 | 중간 |
| 훈련 연계 추천 페이지 | 직무 역량 격차에 따른 훈련 과정 추천 | 낮음 |
| 포트폴리오 생성 페이지 | 이력서/포트폴리오 업로드 및 BridgeWork 양식 생성 | 낮음 |

## 6. 기능 0. 프로필 생성, 온보딩, 로그인/회원가입

### 6.1 기능 목적

사용자가 BridgeWork에 가입하고, 기본 추천에 필요한 정보를 입력할 수 있게 한다.

로그인 방식은 다음을 우선 고려한다.

- 카카오 로그인
- 네이버 로그인

본인인증 기능은 현재 도입하지 않는다.

### 6.2 사용자 입력 정보

회원가입 이후 추천 품질을 위해 추가 정보를 입력받는다.

입력 정보는 다음과 같다.

- 이름
- 나이
- 성별
- 위치정보
- 전화번호

위치정보는 상세 주소가 아니라 동 단위 입력을 우선한다.

예시:

- 서울특별시 마포구 공덕동
- 경기도 수원시 영통구 원천동

### 6.3 위치정보 입력 원칙

위치정보는 사용자의 개인정보 부담을 줄이기 위해 동 단위까지만 입력받는다.

동 단위 위치정보는 다음 목적에 사용한다.

- 생활권 기반 추천
- 통근 가능 범위 계산
- 지역 접근성 지도 초기 위치 설정
- 공고 근무지와의 대략적인 거리 판단

### 6.4 온보딩 UI 원칙

온보딩은 한 화면에 모든 정보를 몰아넣지 않는다.

권장 단계는 다음과 같다.

1. 기본 정보 입력
2. 희망 직무 및 근무지역 입력
3. 통근 범위 및 고용형태 입력
4. 선택 접근성 조건 입력
5. 입력 정보 확인 및 저장

### 6.5 필수 상태 처리

온보딩 화면은 다음 상태를 처리한다.

- 입력 전 상태
- 필수값 누락 상태
- 저장 중 상태
- 저장 성공 상태
- 저장 실패 상태

### 6.6 오류 메시지 예시

나쁜 예시:

- 입력 오류
- 저장 실패
- 잘못된 값입니다

좋은 예시:

- 이름을 입력해주세요.
- 위치 정보는 동 단위까지 입력해주세요.
- 희망 직무를 1개 이상 선택해주세요.
- 통근 범위를 선택해주세요.
- 저장하지 않은 정보가 있습니다. 저장 후 추천을 확인할 수 있어요.

## 7. 기능 1. 직장 필터 생성

### 7.1 기능 목적

사용자가 자신에게 맞는 직장 필터를 생성하고 저장할 수 있게 한다.

직장 필터는 추천 일자리 목록과 접근성 분석에 사용된다.

필터는 최대 3개까지 저장하는 방향을 우선 고려한다.

### 7.2 필수 입력 항목

필수 입력 항목은 기본적인 일자리 추천에 필요한 정보로 구성한다.

- 희망 직무
- 희망 근무지역
- 통근 범위
- 고용형태
- 경력
- 학력

### 7.3 통근 범위 선택값

통근 범위는 다음 선택지를 제공한다.

- 30분 미만
- 30분 ~ 1시간
- 1시간 ~ 1시간 30분
- 1시간 30분 ~ 2시간
- 2시간 이상

### 7.4 선택 입력 항목

장애 유형, 필요한 지원, 선호/기피 업무환경 등은 민감 정보가 될 수 있으므로 선택 입력으로 둔다.

선택 입력 영역에는 다음 안내 문구를 제공한다.

- 더 정확한 접근성 추천을 위해 장애 유형과 필요한 지원을 선택할 수 있어요.
- 입력하지 않아도 기본 일자리 추천은 이용할 수 있어요.

### 7.5 선호/기피 산업

선호 산업과 기피 산업을 입력할 수 있다.

- 선호 산업: 최대 3개
- 기피 산업: 최대 3개

반영 방식은 다음과 같다.

- 선호 산업은 추천 정렬 우선순위에 반영한다.
- 기피 산업은 추천 정렬 후순위에 반영한다.

### 7.6 장애 유형 선택

사용자는 필요한 경우 장애 유형을 선택할 수 있다.

선택지는 다음과 같다.

- 지체장애: 휠체어
- 시각장애: 저시력, 전맹
- 청각장애: 농난청

장애 유형 선택은 필수가 아니다.

### 7.7 필요 지원 선택

사용자는 필요한 지원 항목을 선택할 수 있다.

선택지는 다음과 같다.

- 장애인 표준사업장 해당 여부
- 장애인 전형/우대 공고
- 재택근무 가능
- 유연근무/단축근무 가능
- 근로지원인 연계 가능
- 보조공학기기 지원 가능
- 수어 통역 필요
- 필담/문자 커뮤니케이션 필요
- 전화 응대 적은 업무 선호
- 면접 편의 제공 필요
- 계단 없는 출입 필요
- 조용한 근무환경 선호

### 7.8 기타 선택 항목

추가로 다음 항목을 선택할 수 있다.

- 자격증
- 복리후생
- 우대 전공

### 7.9 저장 전 확인

사용자가 필터를 저장하기 전에 입력 내용을 요약해서 보여준다.

확인 화면에는 다음 정보를 표시한다.

- 희망 직무
- 희망 근무지역
- 통근 범위
- 고용형태
- 경력
- 학력
- 선택한 접근성 조건
- 선택한 필요 지원
- 선택한 선호/기피 산업

### 7.10 필터 목록

사용자는 저장한 필터 목록을 볼 수 있어야 한다.

필터 목록에서는 다음 기능을 제공한다.

- 필터 이름 표시
- 주요 조건 요약
- 대표 필터 설정
- 필터 수정
- 필터 삭제
- 필터 기반 추천 보기

### 7.11 삭제 확인

필터 삭제 시 바로 삭제하지 않고 확인 모달을 제공한다.

문구 예시:

- 이 필터를 삭제할까요?
- 삭제한 필터는 복구할 수 없습니다.

## 8. 기능 1-2. BridgeWork 양식 포트폴리오 생성

### 8.1 기능 목적

사용자가 기존 타 플랫폼 이력서 또는 포트폴리오를 업로드하면, AI가 BridgeWork 양식에 맞는 포트폴리오를 생성한다.

이 기능은 MVP 이후 추가 개발 범위로 둔다.

### 8.2 주요 기능

예상 기능은 다음과 같다.

- 이력서/포트폴리오 파일 업로드
- OCR 기반 텍스트 추출
- 직무 경험 요약
- 보유 역량 구조화
- 희망 직무와의 연결
- 추천 시스템에 활용 가능한 태그 추출
- BridgeWork 양식 미리보기
- 생성 결과 저장

### 8.3 UI 상태

파일 업로드 화면은 다음 상태를 처리한다.

- 파일 선택 전
- 파일 선택 완료
- 업로드 중
- OCR 처리 중
- 생성 중
- 생성 성공
- 생성 실패

### 8.4 예외 처리

다음 상황을 처리한다.

- 파일 형식이 지원되지 않음
- 파일 크기가 너무 큼
- OCR 처리 실패
- 텍스트 추출 결과가 부족함
- 서버 처리 실패

## 9. 기능 2. 맞춤 일자리 추천

### 9.1 기능 목적

실시간 구인 현황, 구직자 프로필, 직장 필터를 바탕으로 사용자에게 적합한 공고 목록을 제공한다.

사용자 화면에서는 “나에게 맞는 일자리” 표현을 우선 고려한다.

### 9.2 추천 목록 표시 정보

추천 공고 카드에는 다음 정보를 표시한다.

- 공고 제목
- 회사명
- 근무지역
- 고용형태
- 직무
- 임금 또는 급여 정보
- 마감일
- 최종 적합도 점수
- 접근성 등급
- 주요 긍정 요인
- 확인 필요 항목
- 장애인 전형/우대 여부
- 재택근무/유연근무 여부
- 관심 공고 저장 버튼
- 상세 보기 버튼

### 9.3 추천 점수 항목

추천 점수는 다음 항목을 조합하여 표시한다.

| 점수 항목 | 의미 | 예시 |
|---|---|---|
| 직무 적합도 | 희망 직무, 경력, 학력, 자격증과 공고의 일치도 | 사무보조 희망, 컴퓨터 활용 가능 |
| 근무조건 적합도 | 고용형태, 근무시간, 재택/하이브리드/탄력근무 여부 | 단축근무 가능, 정규직 선호 |
| 장애 지원 적합도 | 사용자가 필요한 지원을 회사가 제공하는지 | 근로지원인, 보조공학기기, 수어통역, 면접 편의 |
| 업무환경 적합도 | 장애 특성과 업무 부담 요소가 충돌하지 않는지 | 전화응대, 장시간 서기, 소음, 야간근무 |
| 기업 안정성/채용 친화도 | 장애인 고용 경험, 표준사업장, 기업 규모 등 | 장애인 전형, 장애인 우대, 표준사업장 |
| 접근성 요약 점수 | 통근 및 근무지 주변 접근성 요약 | 버스정류장, 엘리베이터, 횡단보도 정보 |

### 9.4 점수 표시 예시

추천 상세 또는 카드 확장 영역에서 다음처럼 표시한다.

- 최종 적합도: 84점
- 직무 적합도: 28/30
- 근무조건 적합도: 17/20
- 장애 지원 적합도: 15/20
- 업무환경 적합도: 14/15
- 기업/채용 안정성: 6/10
- 접근성 요약: 4/5

각 점수에는 설명을 함께 제공한다.

예시:

- 희망 직무인 사무보조와 일치합니다.
- 단축근무 가능성이 있는 공고입니다.
- 장애인 전형 또는 우대 조건이 포함되어 있습니다.
- 장시간 서서 근무하는 업무는 아닌 것으로 보입니다.
- 표준사업장 여부는 확인이 필요합니다.

### 9.5 정렬 및 필터

추천 목록에서는 다음 정렬을 제공한다.

- 추천순
- 접근성 점수 높은순
- 직무 적합도 높은순
- 최신순
- 마감 임박순

필터는 다음 항목을 고려한다.

- 근무지역
- 희망 직무
- 고용형태
- 통근 범위
- 장애인 전형/우대 여부
- 재택근무 가능 여부
- 유연근무 가능 여부
- 표준사업장 여부
- 접근성 등급
- 확인 필요 항목 포함 여부

### 9.6 업무환경 태그

공고에는 다음 업무환경 태그를 표시할 수 있다.

- 사무직 중심
- 현장직 포함
- 고객응대 있음
- 전화응대 있음
- 장시간 서서 근무
- 반복 작업
- 소음 많은 환경
- 야외 근무
- 야간 근무
- 교대 근무
- 무거운 물건 취급
- 빠른 이동 필요
- 세밀한 손작업 필요
- 컴퓨터 사용 중심
- 대면 커뮤니케이션 많음
- 문서 작업 많음

업무환경 태그는 모든 사용자에게 감점으로 표시하지 않는다.

사용자의 선호/기피 조건과 충돌할 때만 주의 또는 확인 필요로 표시한다.

예시:

- 전화응대가 포함될 수 있어 사용자의 선호 조건과 다를 수 있습니다.
- 장시간 서기 여부는 공고 정보만으로 확인이 필요합니다.

### 9.7 추천 목록 상태 처리

추천 목록 페이지는 다음 상태를 처리한다.

- 필터 미선택 상태
- 추천 결과 로딩 상태
- 추천 결과 있음
- 추천 결과 없음
- 추천 결과 불러오기 실패
- 필터 변경 후 재요청 상태

빈 데이터 문구 예시:

- 조건에 맞는 공고를 찾지 못했어요.
- 필터 조건을 조금 넓혀보세요.
- 접근성 조건을 일부 해제하면 더 많은 공고를 볼 수 있어요.

에러 문구 예시:

- 추천 공고를 불러오지 못했어요.
- 네트워크 상태를 확인한 뒤 다시 시도해주세요.
- 다시 시도

## 10. 기능 3. 지역 접근성 지도

### 10.1 기능 목적

구직자 생활권 내 접근 가능한 사업장을 지도와 목록으로 시각화한다.

지역 접근성 지도는 BridgeWork의 핵심 기능이다.

### 10.2 주요 목표

지역 접근성 지도는 다음 목적을 가진다.

- 구직자에게 현실적인 출근 가능 공고를 직관적으로 보여준다.
- 공고 위치 주변의 접근성 정보를 함께 제공한다.
- 휠체어, 시각, 청각 사용자에게 필요한 접근성 확인 항목을 안내한다.
- 추천 공고의 접근성 점수와 근거를 지도에서 확인할 수 있게 한다.

### 10.3 지도 화면 구성

지도 화면은 다음 영역으로 구성한다.

- 검색/필터 영역
- 지도 영역
- 공고 마커
- 접근성 시설 마커
- 공고 목록 패널
- 선택한 공고 요약 카드
- 접근성 근거 패널
- 지도 대신 목록 보기 버튼
- 현재 위치 또는 설정 지역으로 이동 버튼

### 10.4 지도 마커 종류

지도에는 다음 마커를 표시할 수 있다.

- 추천 공고 위치
- 버스정류장
- 지하철역 또는 출입구
- 지하철 엘리베이터 또는 리프트
- 횡단보도
- 음향신호기
- 점자블록 관련 지점
- 교통약자 이동지원센터
- 근로지원인 수행기관

### 10.5 지도 접근성 원칙

지도만으로 정보를 제공하지 않는다.

반드시 목록 형태의 대체 정보를 함께 제공한다.

시각장애 또는 스크린리더 사용자를 위해 다음을 제공한다.

- 공고 위치 목록
- 주변 접근성 시설 목록
- 거리 정보 텍스트
- 접근성 요약 설명
- 선택한 공고의 긍정 요인/확인 필요 항목

### 10.6 접근성 데이터 표시

공고 상세 또는 지도 패널에서 다음 정보를 표시한다.

- 근무지 주변 버스정류장 정보
- 근무지 주변 횡단보도 정보
- 보도턱낮춤 여부
- 음향신호기 여부
- 점자블록 여부
- 지하철 출입구 리프트 정보
- 휠체어 리프트 정보
- 역사 편의시설 정보
- 교통약자 이동지원센터 정보
- 장애인 표준사업장 여부
- 근로지원인 수행기관 정보

### 10.7 데이터 부족 표시

다음 항목은 데이터가 부족할 수 있으므로 확인 필요로 표시한다.

- 건물 내부 엘리베이터 여부
- 근무지 출입구의 계단 없는 접근 가능 여부
- 장애인 화장실 여부
- 저상버스 운행 여부
- 실제 출퇴근 시간대 대중교통 혼잡도
- 실시간 환승 가능 여부

문구 예시:

- 현재 데이터 기준으로는 건물 내부 엘리베이터 여부를 판단하기 어렵습니다.
- 저상버스 운행 여부는 현재 데이터만으로 확인하기 어렵습니다.
- 근무지 출입구의 계단 없는 접근 가능 여부는 지원 전 확인을 권장합니다.

### 10.8 접근성 등급 표시

접근성 등급은 다음 기준을 따른다.

- GOOD: 80점 이상
- CAUTION: 60점 이상
- RISK: 60점 미만

단, RISK라고 하더라도 사용자에게 “불가능”으로 단정하지 않는다.

표시 문구는 다음을 우선한다.

- GOOD: 접근 양호
- CAUTION: 주의 필요
- RISK: 확인 필요 항목 많음

### 10.9 지도 상태 처리

지도 페이지는 다음 상태를 처리한다.

- 위치 설정 전
- 지도 데이터 로딩 중
- 지도 데이터 있음
- 지도 데이터 없음
- 지도 API 로딩 실패
- 접근성 데이터 일부 없음
- 공고 마커 선택 상태
- 필터 변경 후 재로딩 상태

## 11. 기능 3-2. 장애 유형별 접근 경로 추천

### 11.1 기능 목적

직장까지 장애 유형을 고려한 접근 경로 추천을 제공한다.

이 기능은 MVP 이후 추가 개발 범위로 둔다.

중요 판단 요소는 다음과 같다.

- 계단 없는 동선
- 지하철 출입구 리프트 및 역사 편의시설 정보
- 휠체어 리프트
- 보도턱 낮춤 횡단보도
- 버스정류장 접근성
- 장애인 화장실
- 경사로

### 11.3 시각장애 사용자 경로

중요 판단 요소는 다음과 같다.

- 점자블록
- 음향신호기
- 보행자 신호 정보
- 복잡한 환승 여부
- 지도 정보를 대체할 수 있는 텍스트 경로 설명
- 색상에 의존하지 않는 안내

### 11.4 청각장애 사용자 지원

중요 판단 요소는 다음과 같다.

- 문자/채팅 기반 커뮤니케이션 가능 여부
- 전화응대 업무 여부
- 수어 통역 지원 여부
- 필담 가능 여부
- 면접 편의 제공 여부
- 소리 알림에만 의존하지 않는 화면 알림

## 12. 기능 4. 지원 인프라 및 체크리스트 안내

### 12.1 기능 목적

사용자가 공고 지원 전 확인해야 할 정보를 한눈에 볼 수 있게 한다.

이 기능은 공고 상세 페이지에 포함하거나 별도 체크리스트 영역으로 제공한다.

### 12.2 표시 항목

공고 상세 페이지에서 다음 항목을 표시한다.

- 표준사업장 여부
- 장애인 전형 여부
- 장애인 우대 여부
- 근로지원인 수행기관 정보
- 재택근무 가능 여부
- 유연근무 가능 여부
- 면접 편의 제공 여부
- 문자/채팅 커뮤니케이션 가능 여부
- 지원 전 확인사항
- 맞춤형 면접 준비 체크리스트

### 12.3 체크리스트 예시

공고 상세에서 다음 체크리스트를 제공할 수 있다.

- 출입구에 계단 없는 접근이 가능한가요?
- 근무지 건물에 엘리베이터가 있나요?
- 장애인 화장실이 있나요?
- 면접 편의를 요청할 수 있나요?
- 문자 또는 이메일로 문의가 가능한가요?
- 전화응대 업무가 포함되어 있나요?
- 장시간 서서 근무하는 업무가 포함되어 있나요?
- 무거운 물건을 옮기는 업무가 포함되어 있나요?

### 12.4 표시 문구 원칙

지원 전 확인 항목은 사용자를 위축시키는 표현을 쓰지 않는다.

좋은 문구 예시:

- 지원 전 확인을 권장합니다.
- 현재 데이터 기준으로는 판단이 제한적입니다.
- 사용자의 선호 조건과 다를 수 있습니다.
- 일부 항목은 추가 확인이 필요합니다.

피해야 할 문구:

- 지원하지 않는 것이 좋습니다.
- 출근이 불가능합니다.
- 장애인에게 부적합합니다.
- 위험합니다.

## 13. 기능 5. 훈련 연계 추천

### 13.1 기능 목적

희망 직무와 현재 역량의 격차가 큰 경우, 관련 직업훈련 과정을 추천한다.

이 기능은 MVP 이후 추가 개발 범위로 둔다.

### 13.2 추천 대상

훈련 연계 추천은 다음 데이터를 활용할 수 있다.

- 직업훈련 과정
- 구직자 취업역량 강화 프로그램
- 국민내일배움카드 관련 과정
- 장애인 직업훈련 과정
- 직무별 기초 역량 교육
- 자격증 과정

### 13.3 UI 표시 항목

훈련 카드에는 다음 정보를 표시한다.

- 훈련 과정명
- 기관명
- 지역
- 기간
- 관련 직무
- 추천 이유
- 신청 또는 상세 보기 버튼

### 13.4 추천 문구 예시

- 희망 직무와 관련된 기초 역량을 보완할 수 있는 과정입니다.
- 사무보조 직무에 필요한 문서 작업 역량과 관련이 있습니다.
- 현재 선택한 희망 직무와 연결되는 훈련 과정입니다.

## 14. AI 사용 기능 표시

BridgeWork에서 AI가 사용되는 영역은 사용자에게 적절히 안내한다.

### 14.1 AI 사용 영역

AI는 다음 기능에 사용된다.

- 사용자 조건 태그화
- 접근성 추천 결과 설명
- 경로 추천 결과 설명
- 포트폴리오 구조화
- 지원 전 체크리스트 문구 생성
- 훈련 연계 추천 설명

### 14.2 AI 표시 원칙

AI가 생성한 설명에는 다음 원칙을 적용한다.

- 점수 계산은 AI가 임의로 하지 않는다.
- AI는 이미 계산된 점수와 근거를 바탕으로 설명한다.
- 데이터가 부족한 경우 확인 필요로 표현한다.
- 공공데이터에 없는 정보를 있는 것처럼 말하지 않는다.
- 장애 유형만으로 업무 가능 여부를 단정하지 않는다.

### 14.3 사용자 안내 문구 예시

- 이 설명은 공고 정보와 공공 접근성 데이터를 바탕으로 생성되었습니다.
- 일부 항목은 공공데이터만으로 판단하기 어려워 지원 전 확인이 필요합니다.
- AI 설명은 참고용이며, 최종 지원 전 기업에 직접 확인하는 것을 권장합니다.

## 15. 접근성 설계 원칙

BridgeWork는 WCAG 2.2 AA 수준의 접근성을 목표로 한다.

접근성은 단순히 화면을 보기 좋게 만드는 것이 아니라, 사용자가 회원가입, 필터 설정, 공고 탐색, 추천 결과 이해, 지원 준비를 할 수 있게 만드는 것이다.

### 15.1 공통 접근성 원칙

- 버튼은 실제 button 태그를 사용한다.
- 클릭 가능한 div를 남발하지 않는다.
- input에는 label 또는 aria-label을 연결한다.
- 아이콘만으로 의미를 전달하지 않는다.
- 색상만으로 상태를 구분하지 않는다.
- 지도 정보는 목록으로도 제공한다.
- 오류 메시지는 구체적으로 표시한다.
- 폼 제출 중에는 중복 제출을 막는다.
- 모달, 드롭다운, 필터는 키보드 접근성을 고려한다.
- 모바일에서도 버튼과 체크박스의 터치 영역을 충분히 확보한다.

---

## 16. 시각장애 / 저시력 사용자 접근성

### 16.1 화면 설계 원칙

- 모든 버튼, 필터, 공고 카드에 스크린리더용 라벨을 제공한다.
- 아이콘에는 대체 텍스트를 제공한다.
- 지도 마커 정보는 목록 형태로도 제공한다.
- 색상만으로 상태를 구분하지 않는다.
- 명도 대비를 충분히 확보한다.
- 큰 글씨 모드 또는 전반적으로 큰 폰트 설계를 고려한다.
- 고대비 모드를 고려한다.

### 16.2 점수 설명 원칙

“접근성 점수 82점”만 보여주지 않는다.

반드시 점수 이유를 텍스트로 함께 제공한다.

예시:

- 접근 양호: 근무지 주변에 버스정류장과 지하철역 접근성 정보가 확인됩니다.
- 주의 필요: 장애인 화장실 여부는 현재 데이터에서 확인되지 않았습니다.
- 확인 필요: 건물 내부 엘리베이터 정보는 공공데이터만으로 판단하기 어렵습니다.

### 16.3 색상 사용 원칙

초록, 노랑, 빨강만으로 상태를 표현하지 않는다.

항상 텍스트를 함께 표시한다.

예시:

- GOOD: 접근 양호
- CAUTION: 주의 필요
- RISK: 확인 필요 항목 많음

## 17. 지체장애 / 휠체어 사용자 접근성

### 17.1 웹 UI 원칙

- 가능하면 키보드만으로 회원가입, 필터 설정, 공고 탐색이 가능하도록 설계한다.
- 체크박스, 드롭다운, 지도 버튼의 클릭 영역을 크게 만든다.
- 드래그 필수 UI를 지양한다.
- 거리 반경 설정은 드래그만 제공하지 않고 버튼도 제공한다.
- 모바일 버튼과 필터 버튼은 충분한 크기를 확보한다.

거리 반경 버튼 예시:

- 500m
- 1km
- 2km

### 17.2 서비스 기능 원칙

휠체어 사용자에게 중요한 정보는 다음과 같다.

- 휠체어 출입 가능 여부
- 역사 편의시설 및 휠체어리프트 정보
- 장애인 화장실 여부
- 장애인경사로 여부
- 계단 없는 접근 가능 여부
- 지하철 출입구 리프트 위치
- 버스정류장 접근성

저상버스 운행 여부는 현재 동기화 대상에 별도 데이터가 없으면 확정 판단하지 않고 확인 필요로 안내한다.

## 18. 청각장애 사용자 접근성

### 18.1 화면 및 커뮤니케이션 원칙

- 고객센터/상담 문의는 전화만 제공하지 않는다.
- 채팅, 문자, 이메일 등 비음성 문의 수단을 고려한다.
- 영상/음성 안내가 있는 경우 자막을 제공한다.
- 알림은 소리만 사용하지 않고 화면 텍스트 중심으로 제공한다.

### 18.2 공고 상세 표시 항목

청각장애 사용자에게 도움이 되는 공고 정보는 다음과 같다.

- 전화응대 있음
- 대면 커뮤니케이션 많음
- 문자/채팅 기반 커뮤니케이션 가능
- 필담 가능 여부
- 수어 통역 지원 여부
- 면접 편의 제공 여부

## 19. 인지 접근성 / 쉬운 사용성

BridgeWork는 정보량이 많기 때문에 화면 복잡도를 줄이는 것도 접근성의 일부이다.

### 19.1 화면 구성 원칙

- 온보딩을 한 화면에 몰지 않고 단계별로 진행한다.
- 어려운 용어 옆에는 설명을 제공한다.
- AI 추천 결과는 긴 문장보다 요약 카드 중심으로 제공한다.
- 저장 전 확인 화면을 제공한다.
- 오류 메시지는 구체적으로 표시한다.
- 선택지가 많은 경우 그룹화하거나 검색 기능을 제공한다.

### 19.2 용어 설명이 필요한 예시

다음 용어는 사용자에게 설명이 필요할 수 있다.

- 근로지원인
- 보조공학기기
- 장애인 표준사업장
- 장애인 전형
- 면접 편의 제공
- 저상버스 이용 가능 여부
- 계단 없는 출입
- 음향신호기
- 점자블록

### 19.3 오류 메시지 원칙

나쁜 예시:

- 입력 오류
- 잘못된 값입니다
- 실패했습니다

좋은 예시:

- 희망 직무를 1개 이상 선택해주세요.
- 통근 범위를 선택해주세요.
- 위치 정보는 동 단위까지 입력해주세요.
- 저장하지 않은 필터가 있습니다. 저장 후 추천을 확인할 수 있어요.

### 20.1 사용 예정 SourceType

- NATIONWIDE_CROSSWALK
- VOCATIONAL_TRAINING
- JOBSEEKER_COMPETENCY_PROGRAM

### 20.2 프론트 표시 원칙

프론트엔드는 데이터 출처와 판단 기준을 가능한 한 사용자에게 설명한다.

예시:

- 현재 공공데이터 기준으로 확인된 정보입니다.
- 공공데이터에 없는 항목은 확인 필요로 표시됩니다.
- 실제 사업장 환경은 변경될 수 있으므로 지원 전 확인을 권장합니다.

### 20.3 evidence_items 표시

API 응답에 evidence_items가 포함된 경우, 프론트엔드는 이를 근거 정보로 표시할 수 있다.

표시 가능한 항목은 다음과 같다.

- 데이터 출처
- 확인된 항목
- 거리
- 설명
- 기준 시점
- 확인 필요 여부

예시:

- 근무지 주변 300m 이내 버스정류장 정보가 확인됩니다.
- 근처 지하철 출입구 리프트 정보가 확인됩니다.
- 횡단보도 보도턱낮춤 여부가 확인됩니다.
- 장애인 화장실 정보는 현재 데이터에서 확인되지 않았습니다.

## 21. 공고 상세 페이지 명세

### 21.1 표시 영역

공고 상세 페이지는 다음 영역으로 구성한다.

- 공고 기본 정보
- 회사 정보
- 근무 조건
- 직무 내용
- 추천 점수
- 접근성 점수
- 긍정 요인
- 위험 요인
- 확인 필요 항목
- 지도 및 주변 접근성 정보
- 지원 전 체크리스트
- 관심 공고 저장
- 지원하기 또는 외부 링크 이동

### 21.2 추천 설명 영역

추천 설명에는 다음 내용을 포함한다.

- 한 줄 요약
- 왜 추천되었는지
- 사용자의 조건과 맞는 부분
- 주의하거나 확인해야 하는 부분
- 데이터 출처 또는 확인 기준

### 21.3 문구 예시

긍정 요인:

- 장애인 전형 또는 우대 조건이 포함된 공고입니다.
- 공고 정보 기준으로 컴퓨터 사용 중심 업무에 가깝습니다.
- 현재 공공데이터 기준으로 근무지 주변 버스정류장 정보가 확인됩니다.
- 현재 공공데이터 기준으로 근처 지하철역 또는 출입구의 엘리베이터 정보가 확인됩니다.

위험 요인:

- 전화 응대 업무가 포함될 수 있어 사용자의 선호 조건과 다를 수 있습니다.
- 장시간 서기 또는 이동이 필요한 업무일 수 있어 확인이 필요합니다.
- 휠체어 이동에 필요한 역 엘리베이터 또는 리프트 정보가 충분하지 않습니다. 지원 전 확인을 권장합니다.
- 장애인 표준사업장 여부는 현재 데이터에서 확인되지 않았습니다.

## 24. 폼 처리 명세

### 24.1 공통 원칙

폼은 다음 원칙을 따른다.

- 필수값을 명확히 표시한다.
- 검증 오류는 입력 필드 근처에 표시한다.
- 제출 중에는 버튼을 disabled 처리한다.
- 중복 제출을 방지한다.
- 서버 응답 에러를 사용자에게 보여준다.
- 저장 성공 시 사용자에게 명확히 안내한다.

### 24.2 검증 항목

주요 검증 항목은 다음과 같다.

- 이름 필수 입력
- 위치정보 필수 입력
- 희망 직무 1개 이상 선택
- 희망 근무지역 1개 이상 선택
- 통근 범위 선택
- 고용형태 선택
- 필터명 길이 제한
- 전화번호 형식 검증

### 24.3 제출 버튼 상태

제출 버튼은 다음 상태를 가진다.

- 기본 상태
- 입력값 부족으로 비활성화
- 제출 중 비활성화
- 제출 성공
- 제출 실패 후 재시도 가능

## 25. 로딩, 에러, 빈 데이터 처리 기준

### 25.1 Loading

데이터를 불러오는 중임을 사용자에게 보여준다.

가능하면 화면 성격에 따라 spinner 또는 skeleton을 사용한다.

예시:

- 추천 공고를 불러오는 중입니다.
- 접근성 정보를 분석하는 중입니다.
- 저장한 필터를 불러오는 중입니다.

### 25.2 Error

에러 화면에는 다음 요소를 포함한다.

- 사용자가 이해할 수 있는 메시지
- 다시 시도 버튼
- 필요 시 이전 화면으로 돌아가기 버튼

### 25.3 Empty

데이터가 없는 경우 빈 화면을 방치하지 않는다.

예시:

- 검색 결과가 없습니다.
- 등록된 공고가 없습니다.
- 아직 추천 결과가 없습니다.
- 필터 조건을 변경해보세요.

### 25.4 Success

데이터가 정상적으로 있을 때만 본문 UI를 렌더링한다.

데이터가 없을 가능성이 있는 필드는 fallback text를 사용한다.

예시:

- 확인 필요
- 정보 없음
- 공고에서 제공하지 않음

## 26. 성능 및 렌더링 기준

### 26.1 기본 원칙

프론트엔드 코드는 실제 서비스 운영을 고려해 작성한다.

다음 항목을 항상 고려한다.

- 불필요한 리렌더링 방지
- API 요청 중복 방지
- 큰 리스트 렌더링 최적화
- 지도 화면 렌더링 성능
- 이미지 최적화
- skeleton 또는 placeholder 제공
- 사용자 입력 debounce

### 26.2 리스트 렌더링

추천 공고 목록과 지도 마커 목록은 데이터가 많아질 수 있으므로 다음을 고려한다.

- pagination
- infinite scroll
- virtualization
- 고유 id 기반 key 사용
- 필터 변경 시 이전 요청 취소 또는 최신 요청만 반영

### 26.3 검색 및 필터

검색 입력은 필요하면 debounce를 적용한다.

필터 변경 시 과도한 API 요청이 발생하지 않도록 한다.

### 26.4 지도 렌더링

지도 화면에서는 다음을 고려한다.

- 마커 개수가 많을 경우 클러스터링 고려
- 선택된 공고만 상세 정보 표시
- 지도 이동만으로 과도한 API 호출이 발생하지 않게 처리
- 지도 로딩 실패 시 목록 화면으로 대체 가능해야 함

## 27. 표현 정책

### 27.1 피해야 할 표현

다음 표현은 사용하지 않는다.

- 장애인에게 부적합합니다.
- 출근이 불가능합니다.
- 접근할 수 없습니다.
- 지원하지 않는 것이 좋습니다.
- 위험합니다.

### 27.2 권장 표현

다음 표현을 우선 사용한다.

- 확인이 필요합니다.
- 현재 데이터 기준으로는 판단이 제한적입니다.
- 지원 전 확인을 권장합니다.
- 사용자의 선호 조건과 다를 수 있습니다.
- 일부 항목은 추가 확인이 필요합니다.

### 27.3 데이터 부족 표현

데이터가 부족한 경우 다음 방식으로 표현한다.

- 장애인 화장실 정보가 아직 확인되지 않았습니다. 지원 전 확인을 권장합니다.
- 근무지 출입구의 계단 없는 접근 가능 여부는 아직 확인되지 않았습니다.
- 저상버스 이용 가능 여부는 현재 데이터만으로 판단하기 어렵습니다.
- 주변 역 또는 출입구의 엘리베이터·리프트 정보가 충분하지 않습니다.

- 향후 Next.js 페이지 기반 라우팅으로 이전하기 쉬운 구조인가?

## 30. 개발 시 금지 사항

다음 구현은 피한다.

- API 상태 처리 없이 data만 바로 렌더링하는 코드
- 에러를 console.log만 하고 사용자에게 표시하지 않는 코드
- 지도만 제공하고 목록 대체 UI를 제공하지 않는 구조
- 색상만으로 GOOD, CAUTION, RISK를 표현하는 UI
- 장애 유형만으로 업무 가능 여부를 단정하는 문구
- 데이터가 없다는 이유로 접근 불가능하다고 표현하는 문구
- 프론트엔드에서 FastAPI를 직접 호출하는 구조
- 선택 입력이어야 할 민감 정보를 필수로 강제하는 구조
- 한 페이지 파일에 모든 API 로직과 UI를 몰아넣는 구조
- 중복 제출을 막지 않는 폼
- index를 key로 사용하는 대량 리스트 렌더링
- 클릭 가능한 div를 버튼처럼 사용하는 구조

## 31. 최종 구현 방향

BridgeWork 프론트엔드는 단순 구인공고 목록 서비스가 아니라, 장애인 구직자의 실제 지원 가능성과 접근성 판단을 돕는 서비스이다.

따라서 프론트엔드는 다음 세 가지를 항상 우선한다.

1. 사용자가 이해할 수 있는 추천 이유 제공
2. 접근성 정보의 안전한 표현
3. 데이터 부족 상황에서도 신뢰할 수 있는 UX 제공

모든 화면은 “잘 되는 경우”뿐 아니라 “데이터가 없거나 부족한 경우”, “요청이 실패한 경우”, “사용자가 선택 입력을 생략한 경우”를 함께 고려해 구현한다.
